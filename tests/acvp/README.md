# ACVP tests

Tests in this directory validate the implementations in `src/` against
test vectors from NIST's [Automated Cryptographic Validation Protocol (ACVP)](https://pages.nist.gov/ACVP/),
generated by NIST's [usnistgov/ACVP-Server](https://github.com/usnistgov/ACVP-Server)
Gen/Vals.

## ACVP server

The `acvp-server` service generates the ACVP test vectors the tests run
against. Given a registration (the algorithm, mode and parameters to test), it
produces a vector set: the test cases (keys, plaintexts, IVs, ...) and the
expected result for each one.

It's NIST's "Gen/Vals" engine, the code behind NIST's own ACVP servers, built
by [`server/`](server/) from a pinned release into one docker-compose service:

- an Orleans node, which does the crypto for vector generation (the container's
  main process);
- the `GenValAppRunner` CLI, which turns a registration into a vector set by
  sending crypto requests to the node.

Start the server before running the tests (the first start builds the image,
which takes a few minutes), and stop it when done:

```bash
pixi run acvp-up
pixi run test
pixi run acvp-down
```

### Registrations

Each file in [`registrations/`](registrations/) is an ACVP *registration*: the
request the server generates a vector set from. It names the algorithm and
revision to test (`algorithm`, `mode`, `revision`) and declares which
parameters the implementation supports, e.g. for AES-CBC:

```json
{
  "algorithm": "ACVP-AES-CBC",
  "revision": "1.0",
  "isSample": true,
  "direction": ["encrypt", "decrypt"],
  "keyLen": [128, 192, 256]
}
```

The server only generates test cases within those capabilities, so a
registration defines the scope of what is tested. The capability fields differ
per algorithm; each is specified in the algorithm's ACVP spec (linked in the
testtypes.adoc column below). `"isSample": true` is required: only then does
the server include the expected result of every test case in the vector set.
